一句话读懂这个仓库

Ycode 是 AI 编程工作台。它的钥匙是进程模型：桌面端「每窗口一个 Host utilityProcess」， Host 通过 zcode.cjs app-server --stdio 拉起 Agent 子进程；Web 端由 hono server 承载同一套 services， 同样以 stdio 拉起 Agent；终端则直接就是 Agent 本体。三端共享 packages/shared 的协议、 packages/ui 的组件库、packages/rpc 的 7 层 IPC 框架。 架构分层先进，但守护设计的自动化防线（CI / 测试）几乎缺席 —— 这是本次审查的核心矛盾。

改进优先级

完整的问题→影响→方案→迁移步骤见 04-design-improvements.md。以下为摘要卡片。

P0建立 CI 流水线

.github/ 不存在；verify:pre-push 与 distribution-smoke 脚本现成，直接进 Actions，让每次提交获得同一套裁决。

P0补齐测试底盘

按"纯逻辑优先"：v4 wire 编解码往返 → ToolScheduler 拓扑 → permission wildcard → compact 阈值，沿用 node:test 零新依赖。

P1收敛 server-core 双写

zcode-server-cli 的 server-core 是 packages/server/src/http.ts 的复刻；认证/capability 修复需同步两处，有准入不一致风险。

P1架构治理落真

14+ 模块仅 storage 是 managed:true；session 模块声明的入口 contract.ts 根本不存在——声明与代码已漂移。

P1v3→v4 协议收敛

3490 行 zod v3 与约 50 文件的 v4 二进制 wire 并存；先做 method↔command 映射表，双跑 shadow，再删 v3。

P1husky 落地或删除

声明了 prepare:husky + lint-staged，但 .husky/ 无任何被跟踪的 hook 文件——承诺的防护不存在。

P2ui 顶层归拢

packages/ui/src 顶层平铺 100+ 组件（共 609 tsx），按现有域子目录分批搬移，保持源码直出。

P2文档校订

README 称 dev 有 /api/v1/oauth/token 代理但 vite.config.ts 未见；根 AGENTS.md 包清单缺 6 个包。文档即 Agent 的 prompt。

P2评测基建

无 eval/bench；基于 tools/prompt-trajectory 扩展轨迹录制 → 断言 prompt 组装与权限决策的结构回归。
